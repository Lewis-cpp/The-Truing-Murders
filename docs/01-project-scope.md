# 项目范围与 MVP

项目暂定名称：《基于多智能体与状态机的交互式 AI 探案推理解谜平台》。

第一版定位为：**单人、单案件、规则驱动、AI 负责对话表达的完整探案游戏。**

本项目首先是软件工程系统，其次才是 LLM 应用。毕业设计重点放在多角色交互、状态机、知识隔离、确定性规则判定及其测试上，让案件事实、NPC 说法、玩家已知信息和系统判定保持一致。

## 1. 第一版内容预算

| 项目 | 第一版目标 |
| --- | --- |
| 案件 | 1 个预先编写、版本固定的案件 |
| NPC | 4 个可审讯嫌疑人 |
| 场景 | 4 个调查场景，控制在 3～5 个以内 |
| 证据 | 12 条，控制在 10～15 条以内，其中 5 条关键证据 |
| 谎言链 | 3 条，每条包含谎言、反证和承认后的信息 |
| NPC 情绪 | 平静、戒备、紧张、动摇 4 种 |
| NPC 数值 | 压力、信任两个有界数值 |
| 结案结果 | 正确、部分正确、错误；由固定评分规则决定 |
| 存档 | 每个游戏会话自动保存，支持继续与重新开始 |

下文难度为相对于本项目的估计。“高”表示需要重点设计和测试，不意味着必须采用复杂框架。

## 2. MVP 必须实现

| 功能 | 用户价值 | 技术难度 | LLM 依赖 | 毕设适合度 | 主要风险与范围限制 |
| --- | --- | --- | --- | --- | --- |
| 案件定义与载入 | 提供完整、可解的案件 | 中 | 无 | 核心 | 人工编写真相、人物知识、证据和规则；避免设定自相矛盾 |
| 游戏会话与状态机 | 明确调查、指控、结案阶段 | 中 | 无 | 核心 | 防止结案后继续改变调查状态；避免把每种情绪组合都建成游戏状态 |
| 场景探索与证据解锁 | 形成实际调查过程 | 中 | 无 | 核心 | 使用预设地点和调查动作；避免随机发现证据或关键证据永久不可达 |
| 证据背包与详情 | 让玩家整理发现 | 低 | 无 | 高 | 区分客观物证和未经验证的证词，不能把 NPC 的一句话自动当作事实 |
| 4 个 NPC 的自由文本审讯 | 提供核心 AI 交互体验 | 高 | 核心交互依赖 | 核心 | 串角色、泄密、编造事实、注入攻击；每次只提供当前 NPC 获准使用的信息 |
| 简化情绪、压力与信任 | 让交流方式产生反馈 | 中 | 数值变化不依赖；表达依赖 | 高 | 数值随意变化或可被反复刷取；只由明确事件驱动，限制重复事件收益 |
| 谎言、反证与招供机制 | 让证据影响审讯结果 | 高 | 规则不依赖；措辞依赖 | 核心 | 模型自行认罪或随意改口；谎言与承认条件必须预先定义 |
| 证据出示 | 建立取证与审讯的联系 | 中 | 判定不依赖；回应依赖 | 核心 | 出示未持有证据、重复触发效果；由后端校验归属和触发条件 |
| 人物关系图 | 帮助理解人物与动机 | 低至中 | 无 | 高 | 只展示玩家已经知道的预设关系，避免提前暴露秘密 |
| 案件时间线 | 帮助识别时间矛盾 | 中 | 无 | 高 | 展示已发现事件，标注时间精度、来源及“已证实／证词／存疑” |
| 最终指控与规则判定 | 提供明确的游戏目标 | 中至高 | 无 | 核心 | 自由文本难以稳定评分；凶手、凶器、动机、过程要点采用结构化提交 |
| 案件复盘 | 解释推理正确与错误之处 | 中 | 可选 | 高 | 先生成确定性判定与证据解释，再由 LLM 润色；失败时仍可展示固定复盘 |
| 会话记忆与自动存档 | 保证角色和进度连续 | 中 | 无 | 核心 | 保存状态、已触发事件、对话记录；不把完整聊天历史无限塞入上下文 |
| API 异常、成本控制与基础测试 | 保证系统能稳定演示 | 中 | 涉及模型调用 | 核心 | 超时、重复提交、费用失控；设置调用上限、明确失败反馈并验证规则路径 |

### 2.1 自由文本审讯边界

允许玩家自由提问，但关键进度通过明确的证据出示、调查动作和规则条件推动。不能要求模型准确理解任意表达后直接修改状态。

### 2.2 招供与通关边界

NPC 招供是阶段性反馈，玩家应当能够根据足够的证据完成指控。不能把刷满某个隐藏数值设为唯一通关方式。

### 2.3 作案过程判定边界

作案过程判断检查预先定义的关键步骤、顺序或证据关联。玩家可以补充文字解释，但 MVP 不依靠 LLM 对任意长篇推理作最终评分。

## 3. 第二阶段增强功能

以下功能应在完整案件已经可以通关后加入。

| 功能 | 用户价值 | 技术难度 | LLM 依赖 | 毕设适合度 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| 玩家笔记与自建推理板 | 支持主动推理和证据关联 | 中 | 无 | 高 | 拖拽、编辑和保存增加前端工作；玩家假设必须与官方事实分开 |
| 更丰富的 NPC 情绪与对话策略 | 提高角色差异和重玩体验 | 中至高 | 部分 | 高 | 规则组合膨胀，难以解释行为原因 |
| 分级提示系统 | 帮助卡关玩家继续调查 | 中 | 可选 | 高 | 泄露答案；优先按调查进度提供预设提示 |
| 第二个案件与案件校验工具 | 验证系统支持复用 | 中至高 | 无 | 高 | 内容编写成本大；应先复用配置，不复制业务逻辑 |
| 多存档、账号与跨设备继续 | 改善持续使用体验 | 中 | 无 | 中 | 认证、权限和存档版本管理扩大范围 |
| 对话摘要与更精细的上下文压缩 | 支持更长的审讯 | 中 | 可选 | 中至高 | 摘要错误会污染后续对话；事实与状态仍以数据库为准 |
| 流式回复 | 缩短用户感知等待时间 | 低至中 | 依赖模型接口能力 | 中 | 中断、重连和错误处理；按需求考虑 HTTP 流式响应或 SSE |

## 4. 可选创新功能

建议最多选择一项深入实现和评估，避免每项都只有展示效果。

| 功能 | 用户价值 | 技术难度 | LLM 依赖 | 毕设适合度 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| NPC 一致性与越权泄密评测 | 提高角色可信度，形成可量化实验 | 中至高 | 被测对象依赖 | 很高，优先推荐 | 自然语言判定存在模糊性；结合规则检查、人工标注和固定攻击题集 |
| 确定性事件回放与行为解释 | 解释为何解锁证据、提高压力或击破谎言 | 中 | 无 | 很高 | 需要从前期记录事件、输入和规则版本；重点回放状态，不要求复现相同模型措辞 |
| 受约束的 NPC 间信息传播 | 展示更深入的多角色协作 | 高 | 部分 | 有条件适合 | 信息泄露和状态组合快速增加；必须预设传播路径、条件和可传播内容 |

从答辩价值看，“知识隔离与规则约束是否有效”的实验，比单纯增加 Agent 数量更容易形成清楚的研究问题和验证结果。

## 5. 当前不建议实现

| 功能 | 用户价值 | 技术难度 | LLM 依赖 | 毕设适合度 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| 自动生成完整案件 | 增加案件数量与重玩性 | 很高 | 强 | 当前不适合 | 要同时保证真相一致、线索充分、逻辑可解和无死锁，相当于新增一个独立课题 |
| 运行时自动生成关键线索 | 提高表面上的开放性 | 高 | 强 | 不适合当前原则 | 改变客观真相、补造证据，导致确定性判定失去依据 |
| 自主 Agent 群体讨论与投票裁决 | 可能产生丰富叙事 | 高 | 强 | 当前不适合 | 成本、延迟和不稳定性增加；投票不能替代规则判断 |
| 跨案件、跨会话的 NPC 长期记忆 | 增强持续陪伴感 | 高 | 可选 | 当前价值低 | 不同存档相互污染，角色提前知道玩家行为或案件答案 |
| 为单案件建设向量 RAG | 在大规模资料中查找信息 | 中至高 | 通常涉及嵌入模型 | 当前不合算 | 资料量小，直接按权限读取更简单；检索错误或过滤错误可能泄密 |
| 多人联机探案 | 提供合作调查体验 | 高 | 无 | 当前不适合 | 共享状态、并发操作、证据可见性和断线恢复明显扩大范围 |
| 实时语音对话 | 增强沉浸感 | 高 | 涉及语音模型或服务 | 当前不适合 | 增加识别错误、打断处理、延迟和费用，不能直接证明核心推理系统质量 |

AI 可以在开发阶段辅助起草案件，但案件进入游戏前必须经过人工审核并固定版本。这与运行时生成案件属于不同范围。

## 6. 指定功能的 MVP 判断

| 功能 | 是否进入 MVP | 推荐边界 |
| --- | --- | --- |
| 多 Agent | 有限进入 | 4 个隔离的 NPC 角色，共用实现；Host 和 Review 按需执行叙事任务，不做自主循环 |
| 自动生成案件 | 不进入 | 第一版完全使用预设案件 |
| AI 自动生成线索 | 不进入 | AI 可以表达已授权线索，不能创造新的关键事实或证据 |
| NPC 情绪系统 | 进入，简化版 | 4 种情绪、压力和信任两个数值，由规则更新 |
| NPC 谎言机制 | 进入，核心功能 | 预设谎言、触发语境、反证和承认条件 |
| 人物关系图 | 进入，基础版 | 展示已发现关系；不做复杂编辑器和自动推断 |
| 案件时间线 | 进入，基础版 | 从已发现的结构化事件生成，保留矛盾证词的来源 |
| 长期记忆 | 不进入 | 会话内持久状态和有限对话上下文必须有；跨案件记忆不做 |
| RAG | 不进入 | 按 NPC、证据可见性和当前阶段直接筛选数据库记录 |
| WebSocket | 不进入 | 普通 HTTP 足以支撑单人请求与回复；流式体验后续再加 |
| Redis | 不进入 | 第一版由关系数据库存储状态；出现明确缓存或多实例协调需求时再考虑 |
| 多人游戏 | 不进入 | 单玩家、单会话独立状态 |
| 语音对话 | 不进入 | 先完成文本交互闭环 |

多个角色调用同一个模型，不自动证明复杂的多智能体协作。如果保留“多智能体”标题，应清楚定义各角色的知识、状态、行为边界与调度方式，并据实描述交互机制。不要为了匹配标题加入没有玩法价值的 Agent 通信。

## 7. MVP 功能树

```text
交互式 AI 探案平台
├── 案件与会话
│   ├── 载入固定版本案件
│   ├── 创建、继续和重新开始游戏
│   ├── 游戏阶段控制
│   └── 自动保存
├── 调查与证据
│   ├── 4 个场景探索
│   ├── 预设调查动作
│   ├── 12 条证据与解锁规则
│   └── 证据详情、来源和持有状态
├── NPC 审讯
│   ├── 4 个 NPC 的知识与角色隔离
│   ├── 自由文本问答
│   ├── 证据出示
│   ├── 情绪、压力与信任
│   ├── 3 条谎言链与承认条件
│   └── 会话记录与上下文限制
├── 推理辅助
│   ├── 已知人物关系图
│   └── 已知事件与证词时间线
├── 指控与复盘
│   ├── 凶手、凶器、动机和过程要点提交
│   ├── 确定性判定
│   ├── 错误与缺失证据说明
│   └── 结案后的完整真相展示
└── 工程保障
    ├── 输入、权限和状态校验
    ├── 模型超时与失败处理
    ├── 重复请求防护
    ├── 调用次数与 token 用量记录
    └── 规则、知识隔离和通关路径测试
```

## 8. 项目边界

| 边界 | 明确约定 |
| --- | --- |
| 产品边界 | 面向单人完成一个完整案件，不包含社交、交易、排行榜或内容社区 |
| 内容边界 | 凶手、作案方式和关键事实固定；玩家选择影响调查路径和 NPC 态度 |
| AI 权限边界 | 模型只能接收经过筛选的信息并返回文本或受约束的建议，不直接写入证据、真相和结案结果 |
| 状态边界 | 数据库中的会话状态是权威记录；前端展示和模型记忆都不能覆盖它 |
| 知识边界 | 全局真相、NPC 私有知识、允许透露的信息、玩家已知信息分别管理 |
| 判定边界 | 证据解锁、谎言击破、数值变化和结案结果均由确定性逻辑决定 |
| 技术边界 | Vue 3、TypeScript、Element Plus、ECharts 前端；Python、FastAPI、SQLAlchemy 模块化单体后端；MySQL 或 PostgreSQL 二选一；一种兼容 OpenAI 风格接口的模型接入 |
| 性能边界 | 先支撑单人演示和少量并发会话，不预设大规模分布式架构 |
| 成本边界 | 常规审讯每轮原则上一次模型调用；探索、图表、规则判定不调用模型 |
| 可靠性边界 | 模型失败时保留有效存档并允许恢复；对话生成失败不能造成状态重复更新 |

知识隔离应区分“NPC 知道”与“NPC 此刻可以说”。对暂时不允许透露的秘密，优先传入允许的回避说法和解锁状态，减少提前泄密的机会。

规则可以阻止错误文本改变游戏事实，但不能保证自由文本永远不出现幻觉。第一版应通过减少上下文暴露、限制输出用途和固定测试集来降低风险，不能仅凭严格的 Prompt 就认定问题已经解决。

## 9. 开发优先级

| 优先级 | 内容 | 完成标准 |
| --- | --- | --- |
| P0：案件可解 | 真相、证据、谎言链、解锁条件、结案标准 | 人工沿预设路径能够完整破案，没有必须依赖模型猜测的环节 |
| P0：系统可运行 | 会话状态、规则执行、证据获取、指控、保存 | 使用固定回复也能走完完整案件 |
| P1：AI 交互可信 | NPC 知识筛选、文本审讯、情绪表达、上下文与异常处理 | 模型参与后不会获得修改权威状态的权限 |
| P1：达到 MVP | 4 个 NPC、全部场景证据、关系图、时间线和复盘 | 玩家可从开局连续体验至结案 |
| P2：体验增强 | 流式回复、笔记、提示、更丰富的情绪 | 在核心规则稳定后改善体验 |
| P3：创新扩展 | 一致性评测、事件回放或受约束信息传播 | 选一项形成明确实验或技术成果 |

基础校验、存档可靠性和关键规则测试应随功能开发完成，不能留到最后集中补做。

## 10. 推荐开发顺序

1. **编写案件设计稿。** 明确客观真相、4 个 NPC 各自知道什么、12 条证据的来源、3 条谎言链及标准答案，先证明案件可解。
2. **定义最小状态与规则。** 确定游戏阶段、证据持有状态、NPC 数值、谎言状态和规则触发条件。尤其检查“必须先招供才能拿到反证，又必须先拿到反证才能招供”这类循环依赖。
3. **完成不依赖模型的后端闭环。** 支持开局、探索、获得证据、出示证据、指控、结案和继续存档。用固定文本模拟 NPC 回复，验证游戏机制。
4. **接入一个 NPC，走通一条谎言链。** 验证知识筛选、允许说法、情绪表达、模型超时和重复操作处理，通过后再扩展角色。
5. **扩展为完整案件。** 加入其余 NPC、场景和证据，检查证据可达性、不同调查顺序及结案结果。
6. **完成前端完整体验。** 前期用简单页面验证交互，此时补齐审讯、证据出示、关系图、时间线与指控页面。
7. **完成复盘与工程验证。** 检查存档恢复、模型异常、关键规则、注入攻击、知识泄露及单局调用成本。复盘必须能在模型不可用时展示基本结果。
8. **最后选择增强项。** 优先考虑一致性评测或事件回放；只有核心案件稳定后，才增加第二案件、流式体验或其他功能。

## 11. MVP 验收重点

- 玩家能够从开局完整体验到指控与复盘。
- 所有关键状态变化都有确定性规则依据。
- 模型无法绕过程序修改案件事实和结案结果。
- NPC 上下文按照角色、当前状态及信息披露权限筛选。
- 人物关系图与时间线不提前泄露未发现的信息。
- 存档能够恢复，模型异常后游戏仍能继续。
- 核心规则、通关路径、知识隔离和重复操作具有可重复执行的检查。
- 模型调用次数与用量可记录，单局成本能够评估。

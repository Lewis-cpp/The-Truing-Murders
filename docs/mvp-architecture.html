02 /关键链路：玩家出示证据

业务提交与表达提交分开，网络等待不持有数据库锁

01 · 业务事务

校验 → 计算 → 提交

  1. 校验归属、当前会话及幂等键；锁内复核版本、审讯目标与证据持有。
  2. 执行 EVENT → 基础效果 → 击破 → 承认 → 固定披露 → 一次 PROGRESS。
  3. 整体保存状态、事件、效果键、记忆授权段、固定结果和对话占位。
返回 201：证据与披露结果已经保存。
02 · 事务外表达

授权上下文 → 一次生成

  1. Memory 从一致快照构建当前可说内容、近期历史和有来源摘要。
  2. 短事务复核版本、授权段及额度，登记并抢占本次 attempt；提交后发送。
  3. Conversation → Agent Manager → Gateway；校验输出，异常则使用同状态固定回复。
模型候选仅包含文本，不包含玩法效果。
03 · 表达短事务

复核 → 保存 → 展示

  1. 复核当前局、角色、来源版本、memory_epoch、deadline 和 active attempt。
  2. 保存有效表达并结算可得用量；过期候选不覆盖新回复。
  3. 前端轮询已保存结果；明确重试只生成新表达，不再次执行证据规则。
表达失败保留业务结果，使用固定回复。

普通提问：零玩法状态变化

仅受理问答与生成记录，不执行 EVENT，不增加压力或信任，不推进谎言；保存表达不递增 state_version。

最终指控：零模型调用

凶手、凶器、动机、过程与证据关联交由独立 JUDGE 分支评分；同一事务保存正式指控、判定与 REVIEW 阶段。补充文字不参与评分。

双重防重：同一请求键返回原结果；换键重复出示则由一次性效果键防止重复收益。GET 只读，不调用模型或补跑规则。模型用量未知时保留额度占用。

依据：06 证据与规则10 API13 安全与稳定性15 请求路径

03 /游戏状态与 NPC 状态

9 个概念阶段，6 个持久阶段；调查、审讯和指控支持往返

每层谎言单向推进

UNBROKEN→BROKEN→ADMITTED

先满足有效反证，再检查压力或信任等承认条件；深层隐瞒依赖前层承认。数值降低和历史裁剪均不撤销已承认事实。

情绪、承认进度各自派生

压力 / 信任 → 平静、戒备、紧张、动摇。各层承认 → 未承认、部分交代、完整交代。完整交代不等于承认杀人，也不直接决定结案。

程序每轮重建累计获准内容；授权变化递增 memory_epoch，使旧否认与旧摘要退出新上下文。

依据：05 状态机08 分层谎言12 三级记忆

04 /数据架构

CaseTemplate / GameSession / Conversation 三个领域边界，共用一个数据库

21 张表的职责分组（09 篇 20 张 + 12 篇摘要表）
分组物理表权威边界
静态案件 · 9 张case_template · character · character_secret · scene · evidence · evidence_dependency · lie_rule · relationship · timeline_event发布后不可变。每局绑定 template_id；真相、规则和评分配置只供后端按权限读取。
本局状态 · 5 张visitor · game_session · player_evidence · npc_state · accusation匿名归属、阶段、证据、NPC 与单局唯一正式判定。跨表变化原子提交，重开另建新局。
幂等与审计 · 3 张action_request · game_event_log · rule_effect分别记录请求结果、规则依据和一次性效果。事件用于解释，不依靠重放日志恢复存档。
表达与记忆 · 4 张conversation · conversation_message · llm_attempt · npc_memory_summary一轮交互、可见消息、生成尝试及有来源摘要；按本局、版本和 NPC 隔离。
唯一存储原则：state_json 只保留场景进度、非证据已知信息与指控草稿等小结构。证据、NPC、效果键不在其中重复维护；Save/Load 从关系表和剩余 JSON 组装一致的 GameSnapshot。

服务端案件导入

backend/assets/cases/ → 引用与可解路径校验 → 独立维护账号发布静态定义。运行时静态表只读；案件包不随前端静态资源发布。

记忆预算与恢复

近期最多 6 个完整轮次，旧对话采用程序摘录摘要，关键承认每轮从权威状态重建。刷新与恢复不重发模型请求，摘要丢失不影响案件事实。

依据：04 领域模型09 数据库12 记忆扩展

05 /MVP 范围与落地顺序

先用固定回复证明完整案件可解，再加入角色表达

首版必须形成的闭环

  • 创建 / 继续 / 重开 → 4 场景取证 → 4 NPC 文本审讯与证据出示。
  • 12 条证据、5 条关键证据、3 条预设谎言链与基础情绪。
  • 已知关系图、时间线 → 结构化指控 → 三类结果与固定复盘。
  • 自动保存、三级会话记忆、权限隔离、幂等与冲突处理。
  • 模型异常固定降级、调用预算与用量记录、关键测试。

首版之外

自动生成案件 / 关键线索、多人、账号与跨设备、多存档管理、语音、向量 RAG、自主 Agent 讨论与投票。

SSE / WebSocket、Redis、消息队列、语义摘要与 Host / Review 模型润色按后续需要加入。默认固定叙事和复盘已覆盖首版。

领域与案件

固定事实、规则、分层谎言与三类评分。证明无招供也可正确指控。

持久化闭环

建表、迁移、仓储、事务与存档。实库验证锁、约束和幂等。

HTTP 与固定回复

匿名凭据及 API 闭环。模型关闭时仍能完成整局。

单 NPC 表达

接入受限上下文与 Gateway。验证超时、迟到和表达重试。

完整 MVP

扩展全部内容、三级记忆和 Vue 工作台，走通端到端路径。

评测与演示

记录表达违规、固定降级、主备模型质量、实际成本和延迟。

验收门槛：固定回复通关、不同调查顺序、无招供正确路径、重复操作无重复收益、存档恢复、跨角色与跨局隔离、结案冻结、模型故障可继续。程序越权与文本泄密分别评测；本页不宣称这些测试已通过。

依据：01 MVP 范围02 需求14 测试15 开发阶段

06 /设计依据与待定事项

文档编号表示设计细化顺序，不表示功能已完成

本页采用的后续设计约定

以 15 篇的整合表为准：05 篇替代早期三个宏观阶段；09 篇采用 20 张关系表；12 篇新增摘要表，共 21 张；11 篇明确 Vue Router 与 Pinia；13 篇增加主备路由、严格输出协议和有界清理。Memory 的默认程序摘录摘要纳入首版，模型语义摘要仍属后续增强。

实施前仍需落实

完整可发布案件、固定台词、NPC 数值与评分参数、最终数据库和模型供应商、部署资源与实际预算。文档示例不能直接当成正式案件；PostgreSQL 是建议，MySQL 是部署备选，两者只实现一种。性能目标与预算初值需要实测验证。
